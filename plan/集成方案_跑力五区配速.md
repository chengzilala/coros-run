# 集成方案：跑力五区配速（VDOT）加入看板

> 类型：功能集成方案（待评审，未写产品代码）
> 日期：2026-10-10
> 来源：借鉴 `ai-running-coach` 的 `vdot_calculator.py`（MIT），**内化**为本项目自己的纯函数
> 约束：**不依赖 Claude、不新增用户操作、零第三方依赖、兼容本机 Python 3.9**
> 关联：[可行性分析_ai-running-coach借鉴.md](./可行性分析_ai-running-coach借鉴.md) ｜ [RPD_需求文档.md](./RPD_需求文档.md)

---

## 一、目标与范围

把「丹尼尔斯 VDOT 五区配速」算出来，**展示在看板上**，让用户一眼知道"我该用多快跑轻松跑 / 阈值跑 / 间歇"。

- **本次只做**：VDOT 推算 + E/M/T/I/R 五区配速展示（只读展示，不参与任何自动调整）。
- **明确不做**（留给以后）：周训练建议/课表（功能③）、Readiness 状态灯（功能②）、分享图（功能④）。
- **定位**：看板的"体能放大镜"——把高驰已有数据（完赛预测）翻译成"训练该跑多快"，**不加新数据源**。

---

## 二、用户会看到什么（零负担）

- 看板体能区**新增一张卡片**：「训练配速 · 五区」，表格五列：轻松跑 E / 马拉松 M / 阈值 T / 间歇 I / 冲刺 R。
- 卡片顶部一行小字标注**依据**，如：「依据 半马预测 1:42:14 · VDOT 41」。
- 数据缺失 / 超出查表范围时，**优雅显示"—"**，绝不臆造。

**零负担**体现为：用户还是老流程（`fetch_data.py` 抓数 → 打看板），**不装东西、不碰 Claude、不进新页面、不用额外勾选**。

---

## 三、数据来源与口径（含实测）

### 3.1 数据来源：现有 `dashboard.json` 里的完赛预测，**零新增抓数**

当前 `fitness.predictions` 已有（本机实抓）：

```json
{ "5 km": "21:59", "10 km": "45:39", "Half Marathon": "1:42:14", "Marathon": "3:35:42" }
```

### 3.2 口径：用「比赛成绩 → 查 VDOT 表 → 出五区配速」（丹尼尔斯标准做法）

**锚点选择优先级**：`Half Marathon` → `10 km` → `5 km` → `Marathon`（半马最稳、样本足；全马预测偏差最大，降为末选）。

### 3.3 实测验证：四条预测互相印证（关键证据）

| 锚点 | 预测成绩 | 换算秒 | 最接近的 VDOT |
|---|---|---|---|
| 5 km | 21:59 | 1319 | **41**（表 1308，差 11） |
| 10 km | 45:39 | 2739 | **41**（表 2748，差 9） |
| 半马 | 1:42:14 | 6134 | **41**（表 6174，差 40） |
| 全马 | 3:35:42 | 12942 | **41**（表 12828，差 114） |

→ **四条都指向 VDOT 41**，口径自洽，可放心用。对应五区配速（本机实跑脚本得出）：

| 区 | 含义 | 配速 |
|---|---|---|
| E | 轻松跑 | 5:54 ~ 6:27 /km |
| M | 马拉松配速 | 5:33 /km |
| T | 阈值跑 | 5:15 /km |
| I | 间歇 | 400m 1:52 / 1000m 4:52 |
| R | 冲刺 | 200m 0:52 / 400m 1:48 |

### 3.4 ⚠️ 一个必须标清的口径坑

COROS 另有「**阈值配速 = 4:35/km**」，若拿它反查，会得到 **VDOT≈50**——**与上面 VDOT 41 相差 9 档**。原因是两个口径的定义不同（COROS 阈值配速偏乐观）。

**处理规则**：**只采用"完赛预测"这一条口径**，并在卡片上标"依据 半马预测…"，**不混用**、不解释成"跑力值"。同时明确：**VDOT ≠ COROS 的 VO2max（53）/ 跑力值（83）**，三者是不同量表，界面不并列比较，避免用户困惑。

## 四、技术方案

### 4.1 算在哪：后端抓数时算好，写进 `dashboard.json`（推荐）

数据流保持现状不变：`fetch_data.py` → `dashboard.json` → `app.js` 渲染。**把计算结果固化成数据的一个字段**，前端只渲染、不算数（符合本项目"数据在后端、前端只展示"的分层）。

- 备选（不推荐）：在 `app.js` 里放表算。省一次重抓，但把大表塞进前端、且与后端分层相悖。

### 4.2 新增一个纯函数模块（移植 + 适配）

- 新建 `tools/pace.py`：从 `ai-running-coach/vdot_calculator.py` 移植 **VDOT 对照表**与五个纯函数。
- **必改**（否则本机跑不起来）：它原码用了 `float | None` 注解（需 Python 3.10+），本机是 **3.9.6** → 一律改成 `Optional[...]` 或去掉注解。**不要照抄**。
- 保持**纯标准库**（`argparse` / `math` 已足够），符合项目"零第三方依赖"红线。
- 对外只暴露两个函数：`vdot_from_race(dist_key, seconds)` 和 `paces_for_vdot(vdot)`；越界**抛错**（不静默钳制），由调用方降级为"—"。

### 4.3 接入抓数脚本

- `tools/fetch_data.py`：在 `main()` 组装 `out` 时，用 `fitness.predictions` 调 `pace.py`，写入：

```json
"fitness": {
  "vo2max": 53.0, "runningLevel": 83.0, "thresholdPaceSec": 275,
  "predictions": { ... },
  "paces": {
    "vdot": 41,
    "anchor": "Half Marathon",
    "anchorTime": "1:42:14",
    "E": "5:54~6:27", "M": "5:33", "T": "5:15",
    "I_400m": "1:52", "I_1000m": "4:52", "R_200m": "0:52", "R_400m": "1:48"
  }
}
```

- 解析失败/无预测/越界 → 不写 `paces`（前端自然不显示该卡片）。

### 4.4 前端渲染

- `web/index.html`：在 `.board-main` 里新增一张卡片（建议紧挨「训练负荷」或放进体能区）：

```html
<section class="card">
  <h3>训练配速 <span class="hint" id="paceHint"></span></h3>
  <div id="paceTable" class="pace-table"></div>
</section>
```

- `web/app.js`：新增 `renderPaces()`（读 `DATA.fitness.paces`；无则整卡隐藏或显示占位），在 `init` 的 `renderHero(); renderKpis(); …` 之后调用一次。
- `web/style.css`：复用现有卡片/pill 风格，加一个五列小表（手机端可两列折行）。

## 六、关键约束（self-check）

- ✅ **不依赖 Claude**：纯本地 Python 函数，与 LLM 无关。
- ✅ **不新增用户操作**：仍是"抓数 → 看板"两步。

- ✅ **兼容 Python 3.9.6**：不写 `X | None`。

- ✅ **只读**：不写高驰、不动用户账号。

## 八、风险与坑

| 风险 | 说明 | 应对 |
|---|---|---|
| **Python 版本** | 原码 3.10+ 语法，本机 3.9.6 直接报错（已实测 `readiness_calc.py` 崩） | 移植时改成 3.9 兼容写法 |
| **口径不一致** | COROS 阈值配速反查得 VDOT≈50，与完赛预测的 41 差 9 档 | 只用"完赛预测"一条口径 + 界面标注依据，不混用 |
| **概念混淆** | VDOT / VO2max / 跑力值是不同量表 | 卡片不并列比较，也不解释成"跑力值" |
| **预测质量** | COROS 预测是模型值，非实测成绩 | 标注"依据预测"，措辞不写"实测" |
| **重抓才更新** | 结果在抓数时固化 | 可接受；用户本就会重抓。若想免重抓，改前端算（备选方案） |
| **表格时效** | VDOT 表来自丹尼尔斯 2013 版 | 表内注释标版本来源，便于日后核对 |
