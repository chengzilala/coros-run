## 一句话结论

**它 = 「Claude 健身教练 Skill」+「一个能部署的数据看板」。看板我们已经有（而且更省事：自动抓数 + 内建 AI 复盘 + 账户体系）；教练那一半我们完全没有。不建议整体照搬，建议按需借鉴 3 块。**

- **数据看板 / KPI / 趋势图 / 详情**：⚠️ **我们有，形态相近但内核不同**——我们是「高驰接口 → 自动拉数 → 网页」，它是「本地 Obsidian 笔记 → 脚本解析 → 静态页」，它的数据得先靠 Skill 写进笔记才有。
- **AI 复盘**：✅ **我们有，它反而没有**（它的 AI 在 Skill 里，不在看板上）。
- **账户 / 多用户**：✅ **我们有，它完全没有**（它是单机静态页，前端口令门，无账号）。
- **训练课表 / Readiness / ACWR / 多运动领域（越野·Hyrox·力量·营养·生理·康复）/ 知识卡**：❌ **我们完全没有，而这正是它的核心价值**。
- **是否必要**：**不建议整体照搬**（定位不同：它是「给 Claude 看的方法论 + 看板」，我们是「产品」）；**建议按需借鉴 3 块**（见第五节），其中**算法理论 notes/** 与**看板的几种图表表达**最值得吸收。

> ⚠️ 先纠正一个前提：**它不是一个"独立可用"的产品**。它的核心是一份 41KB 的 `fitness-coach.md`（写给 Claude Code 的 Skill），要在 Claude / 支持 MCP 的客户端里跑；其中的 `dashboard/` 只是**读本地笔记的静态展示页**，本身不产生数据、不接高驰。所以"我们有没有这个功能"，要**拆成两半**分别回答。

## 一、我们俩到底各有什么（真实用户 / 证据）

两者都在用**高驰官方 MCP**（只读），但**形态与用途不同**：

| 维度 | 我们 `coros-run` | 它 `claude-fitness-cn` |
|---|---|---|
| 形态 | **网页产品**（本机看板 → 对外多用户版在建） | **Claude Skill** + 一个**读本地笔记的静态看板** |
| 数据来源 | 高驰官方 MCP **自动抓取**（`us` 区） | 高驰官方 MCP（用 `cn` 区；Skill 抓）→ 写进**本地 Obsidian 笔记** → 看板读笔记 |
| 看板技术 | 原生 HTML/CSS/JS + **本地 ECharts（无 CDN）** | 静态 SPA + **CDN 加载 Chart.js**（jsdelivr） |
| 看板内容 | 跑量/配速/心率/负荷 + **AI 中文复盘** + 活动详情 | 赛事倒计时/PB、越野、Hyrox 雷达、力量 Volume Load、跑步分析、恢复、**营养、生理、康复** |
| AI 能力 | **在看板内**（自定义 Key，四段复盘） | **在 Skill 内**（`/fitness-coach morning/evening/weekly/plan`），看板无 AI |
| 账户体系 | ✅ 本机原型 + 对外版（CloudBase）在建 | ❌ 无（仅前端口令门 `PASSCODE`，非真安全） |
| 目标用户 | 先自己 → 再对外 | 开源分享（个人模板，未见商业产品） |
| 商业化 | 未见（先自用） | 未见（MIT 模板） |

**关键差异（如实讲）**：
- **数据链路反着来**：**我们"自动进"**（跑一条命令就抓数），**它"手动/半自动进"**（得先把数据落成 Obsidian 笔记）。所以它的看板**不能脱离那套 Skill / 笔记单独用**。
- **看板"长得像"，但一句话概括：它偏"备赛工具箱"，我们偏"跑后复盘"**。它把越野/Hyrox/力量/营养/生理/康复都铺开；我们聚焦"跑量-配速-心率-负荷 + AI 说人话"。

> 与备忘录里另一个链接的关系：`ai-running-coach`（本目录已有分析）与本文对象是**两个独立仓库**，都是"Claude 教练 Skill + 高驰 MCP"，**都没有账号体系**；区别是本文对象**多了一个能部署的看板**，且**领域更宽（多运动/营养/康复）**。

## 四、可借鉴路径对比

| 路径 | 具体做什么 | 能否 | 门槛 | 用户要不要装新东西 | 风险 |
|---|---|---|---|---|---|
| **A. 整体照搬 Skill** | 把它的 `fitness-coach.md` + `notes/` 作为 Claude 技能引入，与看板并行 | ✅ 能 | **低**（MIT，克隆即用） | **要**（得有 Claude/MCP 客户端） | 形态割裂：两套东西，非我们的产品 |
| **B. 借鉴"目标参考线"图表表达** | 给我们的图加"目标/基准虚线 + 脚注洞察"（周目标、比赛 REC、30s 踝稳定那种） | ✅ 能 | **低**（纯前端） | 否 | 无；纯视觉增强 |
| **C. 借鉴"80/20 强度分布 + 心率效率"** | 用现有数据加两张跑步分析图（轻松/高强度占比、速度÷心率） | ✅ 能 | **低**（数据已有） | 否 | 无；和我们定位最契合 |
| **D. 做 Readiness 就绪灯** | 抓 HRV/静息心率/睡眠 → 顶部"今日状态灯" | ✅ 能 | **中** | 否 | 补我们的 **F8**；数据官方 MCP 已有 |
| **E. 借它的 notes/ 算法口径** | 读 `training-load-encoding.md` / `readiness.md` / `nutrition.md`，把"确定性公式不交给 AI""无数据不推断"写进我们复盘 prompt | ✅ 能 | **低** | 否 | 内容须合规审（健康建议标"仅供参考"） |
| **F. 复刻营养/生理/康复等专项视图** | 把它的赛事/越野/Hyrox/营养/康复整套搬进我们看板 | ⚠️ 半 | **高**（数据源 + 大量视图 + 合规） | 否 | 大幅改定位；且很多数据我们现在**抓不到**（饮食、体围、伤病需手动录） |
| **G. 做完整"AI 训练助手"产品** | 我们自己做课表生成 + 周调整（网页形态） | ⚠️ 半 | **高** | 否 | 同 ai-running-coach 结论：**课表回写手表做不到**（官方 MCP 只读） |

**各路径真实差异（如实说）**：
- **B/C/D/E 是"长进我们自己的产品里"**，不改定位、成本低，**体验统一**——**推荐区**。
- **F 看着诱人但坑最深**：它的营养/生理/康复**大量依赖手动录入**（饮食来自微信机器人、体围/伤病来自 `curated` 手填），**不是自动抓来的**；我们"自动抓数"的优势在那些板块**根本用不上**。**别被截图骗了**。
- **G 不重复**：与 ai-running-coach 分析里的结论一致——真正"教练产品"是另一条线。

## 五、推荐方向 + 最小验证清单

### 推荐方向

- **主线（推荐）= C + B + E**：**只借"和我们跑步看板契合、成本低"的三块**——
  1. **跑步分析增强**（80/20 强度分布、心率效率趋势）——数据我们已有；
  2. **图表"目标参考线 + 洞察脚注"**——纯前端视觉升级，立刻好看；
  3. **它的 notes/ 算法口径**——把"确定性算术不交给 AI""无数据不推断"写进我们 AI 复盘。
  - 理由：**不改变"跑步看板 + AI 复盘"定位**；**技术省事**。
- **备选 = D**：把 **Readiness 就绪灯**做进看板（正式启动我们的待办 **F8**）。这是它最实用、且我们**能自动拿到数据**的一块。
- **兜底 = 只借思路**：连图表都不加，只借它**"目标线/洞察文案"**的产品表达，写进我们看板的信息层级。
- **暂不建议 = F / G**：F 要搬的板块**多数数据我们现在拿不到**（饮食/体围/伤病靠手填），投产出比低；G 是另一条产品线，且课表回写手表不可行。

### 先讲清取舍

- 选 B/C/E 是**"技术省事"**（拿现成表达与准则）；选 D/F 是**"产品形态"**（把看板往"教练"方向推）。**两者不冲突**，但 F 的性价比明显偏低。
- **真正要你拍板的只有一件事**：**产品是"跑步看板"，还是"多运动备赛工具箱"？**
  - 若坚持**跑步看板** → 做 **C+B+E** 就够，**不必要**碰它的专项板块；
  - 若想扩成**备赛/多运动** → 先做 **D**，再**单独评估 F**（且要先解决"数据怎么来"）。

### 最小验证清单（不写产品代码即可验证）

- [ ] **1. 看它的看板**（本机已跑）：浏览器打开 `http://127.0.0.1:8945/`（口令 `changeme`），逐屏看。成本 ¥0。
  - 判定：有 3 处以上"想搬进我们看板" = **通过**；觉得平平 = **半通过**。
- [ ] **2. 对拍"80/20 强度分布 + 心率效率"**：用我们自己的高驰数据，手算一次轻松/高强度占比与`速度÷心率`，看是否有洞见。成本 ¥0。
  - 判定：能看出"练得偏不偏/进没进步" = **通过**（值得加）；看不出 = **不通过**。
- [ ] **3. 试它的 Skill**：在 Claude Code 挂高驰 MCP，加载它的 `fitness-coach.md`，跑一次 `morning`（就绪）与 `weekly`（周复盘）。成本 ¥0。
  - 判定：就绪分/周复盘**逻辑自洽、能指导训练** = **通过**（则 D 值得投入）；输出空泛 = **半通过**。
- [ ] **4. 读它的三篇算法 notes/**：`training-load-encoding.md` / `readiness.md` / `nutrition.md`。成本 ¥0。
  - 判定：有可复用的公式口径 = **通过**（并入我们 prompt/计算）。
- [ ] **5. 需求确认（最关键）**：问自己——"我打开产品，最想看到的是**这次跑得怎样**，还是**下周/这场赛该怎么练**？"
  - 判定：只想看复盘 = **维持跑步看板**（做 C+B+E）；想要备赛指导 = **进入教练方向**（先 D 再议 F/G）。

> **决策规则**：1+2 通过 → 借鉴 C/B 有底；3 通过 → 追加 D；5 若"想备赛"占上风 → 才考虑 F/G。

## 六、隐藏坑（预期落差 / 政策时效 / 平台限制）

1. **看板不能独立用（最大坑）**：它的 `dashboard/` 只**读本地 Obsidian 笔记**（`build-data.mjs` 解析 Markdown），**不接高驰、不抓数**。没有 Skill 先把笔记写出来，看板就是空的。**别以为"克隆下来就有一个自带数据的网站"。**
2. **它自己承认高驰缺 data**：README 表格写明 **Coros 无 Body Battery、无 ACWR** → Readiness 只能跑"缩水版"（用主观 1-5 问题代替）。**这和我们自己分析过的"官方 MCP 只读、能力有限"一致**。想自算 ACWR，得用它的两池负荷模型（见 notes）。
3. **CDN 依赖（与我们规则冲突）**：它看板用 **CDN 加载 Chart.js**（`cdn.jsdelivr.net`）。我们项目的规则是**"本地 ECharts、不引 CDN"**。若要借鉴它，**不能连 CDN 一起搬**，得换成我们的本地图表库。
4. **需要 Node/npm（本机没有）**：它的看板构建用 `npm run sample` / `data`（`build-data.mjs`）。**本机 `node`/`npm` 未安装**，本次是用 Python 静态服务直接服务 `public/` 才跑起来的（sample 数据已随仓库提供，可直接看）。
5. **区域/口径坑（它已踩）**：它提示中国区高驰账号必须用 `region="cn"`（`teamcnapi.coros.com`），用 `us`/`eu` 会"看似登录成功、实则数据调用全失败"；另注 `卡路里是 milli-kcal（要 ÷1000）`、`max_hr 常为 null`。**这些是我们抓数也会遇到的坑**，值得记进 `fetch_data.py` 的解析备注。
6. **合规红线**：它的**营养/生理/康复**内容含健康建议，我们的红线是「**不做医疗诊断、结论标"仅供参考"**」。借鉴必须改写口径。
7. **同源问题**：既然**同用高驰官方 MCP**，接口变动与限额**我们一个都跑不掉**——别把它当"更稳的数据源"。
8. **时效性**：仓库最近提交为 **2026-08-17**（约 2 个月前），MCP 工具名/端点可能已变；实跑/对接前先核对。
