## 一句话结论

**它和我们不是一回事，谈不上"我们有没有这个功能"——我们是「展示层」，它是「决策层」，互为补充而非重复。**

- **数据看板 / 图表 / 活动详情 / AI 复盘界面 / 账户 / 多用户**：✅ **我们有，而且它完全没有**（它连网页界面都没有）。
- **训练课表生成 / 每周动态调整 / VDOT 五区配速 / Readiness 恢复判定 / 伤病·力量·营养知识卡 / 周打卡图**：❌ **我们完全没有，而这些正是它的核心价值**。
- **是否必要**：**不建议整体照搬**（形态根本不同：它是"给 AI 看的方法论 + 计算脚本"，跑在 Claude 里，不是产品）；**建议按需借鉴 3 块**（见第五节），其中「确定性计算脚本」和「Readiness 判定」与我们最契合、可低成本吸收。

> ⚠️ 先纠正一个前提：**这个项目没有浏览器界面**。它是 **Claude Skill**（一套写给 AI 的规范 + 知识卡片 + 4 个 Python 脚本），要在 Claude / 支持 MCP 的客户端里跑。所以你设想的"本地启动 → 浏览器里判断"**对它不适用**——它唯一能进浏览器的东西，是它**生成出来的"周打卡图" HTML**。要判断值不值得借鉴，只能**读它的源码**（我已读完，见下）。

## 一、我们俩到底各有什么（真实用户/证据）

两者**都在用同一套高驰官方 MCP**（只读），数据来源一样；差别在**拿数据干什么**：

| 维度 | 我们 `coros-run` | 它 `ai-running-coach` |
|---|---|---|
| 形态 | **网页产品**（本机看板 → 要做多用户对外版） | **Claude Skill**（无 UI，跑在 Claude 里） |
| 数据来源 | 高驰官方 MCP（`us` 区） | 高驰官方 MCP（README 用 `cn` 区端点） |
| 核心用途 | **把数据做得好看 + 中文复盘** | **给用户排训练课表 + 每周调整** |
| 产物 | 网页看板 / 图表 / 弹窗详情 | Markdown 课表 + 周打卡图 HTML |
| 目标用户 | 先自己 → 再对外 | 开源分享（背后有托管版产品 Pacer） |
| 商业化 | 未见（先自用） | ✅ 有：托管版 **Pacer**（"这份仓库是它的开源方法论层"） |

**关键洞察**：README 自己写明「**本仓库 = 方法论，可自托管；Pacer = 同一套逻辑的产品化托管版**」。也就是说，**你要做的"网页产品"这件事，它其实也没做（是它背后的 Pacer 在做）**。所以：
- 论"网页看板"，**我们是它没有的东西**；
- 论"训练教练"，**它是我们缺的一整块**。

它不是竞品，是**另一条产品线**。

## 三、逐条判定：我们"有 / 没有"这个功能

| 它的功能 | 我们现状 | 判定 | 依据 |
|---|---|---|---|
| 高驰数据看板（KPI/趋势图/列表/详情） | ✅ 已有 | **我们更强** | 我们是网页产品；它没有 UI |
| AI 中文复盘 | ✅ 已有（总览/亮点/问题/建议四段） | **我们已有** | `web/app.js` + `/api/review` |
| AI Key 托管 / 账户 / 跨设备 | ✅ 已有（本机原型 + 对外版在建） | **我们已有** | RPD §10、§11 |
| 训练**课表生成** | ❌ 无 | **它是核心，我们缺** | 无对应模块 |
| 每周**动态调整**课表 | ❌ 无 | **我们缺** | 无对应模块 |
| **VDOT 五区配速**（自算） | ⚠️ 半 | **我们只"展示"不自"计算"** | 我们只显示高驰自带的跑力/VO2max/阈值配速（`parse_fitness`），没有自己的 VDOT 表 |
| **Readiness 红旗判定** | ❌ 无（列为待办 F8） | **我们缺，且数据已能拿到** | 我们能抓 `queryTrainingLoadAssessment`/`queryDailyHealthData`；HRV/睡眠/静息心率是官方 MCP 现成工具 |
| 湿热按课型调整 | ❌ 无 | 我们缺 | 无对应逻辑 |
| 伤病/力量/营养知识卡 | ❌ 无 | 我们缺 | 无对应内容 |
| 周打卡分享图 | ❌ 无（但有"分享卡"母本经验） | 我们缺 | 无导出图功能 |
| 独立可用（无需 Claude） | ✅ 我们是网页，零门槛 | **我们更强** | 它必须挂在 Claude/MCP 客户端上 |

**结论**：**"看"的部分我们全有且更强；"教"的部分我们全没有。** 你要判断的就是——**产品到底要不要从"看板"扩到"教练"**。

## 四、可借鉴路径对比

| 路径 | 具体做什么 | 能否 | 门槛 | 用户要不要装新东西 | 风险 |
|---|---|---|---|---|---|
| **A. 整体照搬它的 Skill** | 把它的 SKILL+知识卡+脚本作为独立技能引入，与看板并行（看板看数据、Claude 出课表） | ✅ 能 | **低**（克隆即用，MIT） | **要**（用户得有 Claude/MCP 客户端） | 形态割裂：两个东西分开，不是我们的产品；非 Claude 环境体验差 |
| **B. 只搬"确定性计算脚本"** | 把 `vdot_calculator.py` / `readiness_calc.py` / `nutrition_calc.py` 移进我们 `tools/`，把"AI 不做心算"落成我们的红线 | ✅ 能 | **低**（纯标准库、纯函数、MIT） | 否 | ⚠️ 它是 Python 3.10+ 语法，本机是 **3.9.6**，**要先改**（见隐藏坑） |
| **C. 把 Readiness 做进看板** | 抓 HRV/静息心率/睡眠 → `readiness_calc` 逻辑 → 看板顶上一盏"今日状态灯" | ✅ 能 | **中**（要加抓取 + 视图） | 否 | 补我们待办 **F8**；数据官方 MCP 已有 |
| **D. 借鉴知识卡片"场景路由"思路** | 把我们 AI 复盘从"通用四段"升级为"按问题路由到结构化知识" | ✅ 能 | 中 | 否 | 内容需自备/合规审（健康建议须标"仅供参考"） |
| **E. 借鉴周打卡图规范** | 按它的"Hero-Share v4"规格 + 设计 token，给看板加"一键导出分享图" | ✅ 能 | 中 | 否 | 我们有分享卡母本经验，成本可控 |
| **F. 做完整"AI 训练教练"产品** | 我们自己做课表生成 + 回写 + 周调整（网页形态） | ⚠️ 半 | **高**（要 LLM 长结构化输出 + 前端整套 UI） | 否 | **课表回写手表做不到**：官方 MCP 全只读（它自己在 ADAPTERS.md 里证实），只能出图/出文档 |

**各路径的真实差异（如实说）**：
- **A vs B/C**：A 是"把别人的工具摆旁边"，**零开发但要用户自己会玩 Claude**；B/C 是"长进我们自己的产品里"，**要开发但体验统一**。两者体验**并不一样**，别混。
- **C 和 F 别混**：C 只是"看板加一盏状态灯"（小）；F 是"做一个教练产品"（大）。名字都叫"训练建议"，工作量和定位差一个数量级。

## 五、推荐方向 + 最小验证清单

### 推荐方向

- **主线（推荐）= B + C + E**：**只把"与我们展示定位契合、可低成本吸收"的三块借鉴进来**——
  1. **确定性计算脚本**（VDOT/readiness/nutrition，改 3.10 语法后可入 `tools/`）；
  2. **Readiness 状态判定**（补我们的 **F8**，看板加"今日状态灯"）；
  3. **周打卡分享图**（复用我们分享卡经验，按它的规格做导出）。
  - 理由：这三块是**"看板 + 复盘"的自然延伸**，不改变产品定位；**技术省事**。
- **备选 = A**：如果哪天你想"马上有个能排课表的教练"，**直接把它的 Skill 克隆引入**（成本几乎为零），当独立工具用，先跑顺再谈产品化。**注意它只能在 Claude/MCP 客户端跑。**
- **兜底 = 只借思路不借代码**：连脚本都不用，只借它**"确定性算术不交给 AI"**和**"无数据不推断"**两条工程准则，写进我们自己的 AI 复盘 prompt。
- **暂不建议 = F**：做完整"教练产品"是**另一条产品线**（长结构化输出 + 整套前端 + 出图），且**课表回写手表做不到**。除非你确认"排课表"才是你真正要的，否则别开这条线。

### 先讲清取舍

- 选 A/C/E 是**"产品形态正确"**（让看板更完整、更像产品）；选 B/D 是**"技术省事"**（拿现成纯函数/准则）。**两者不冲突**，可同时做。
- **真正要你拍板的只有一件事**：**产品是"看板"还是"教练"？** 若坚持看板 → 做 B+C+E 就够，**不必要**整体引入它；若想要教练 → 先走 A 零成本验证，再决定是否投入 F。

### 最小验证清单（不写产品代码即可验证）

- [ ] **1. 零成本试它的 Skill**：在 Claude Code / Claude Desktop 挂上高驰 MCP，把它的 `SKILL.md` + `knowledge_cards/` 加进去，跑一次「初始化 → 生成课表 → 更新本周数据」。成本 ¥0。
  - 判定：生成课表**结构完整、配速自洽、能根据实跑调整** = **通过**（方向值得投入）；输出截断/乱配速 = **半通过**；无法挂载 = **不通过**（则只借思路）。
- [ ] **2. 跑通它的三个脚本**：`vdot_calculator.py --distance 5K --time 22:00`（已验证可用，见附录）；`readiness_calc.py`、`nutrition_calc.py`（**本机需先升级到 Python 3.10+**）。成本 ¥0。
  - 判定：脚本结果**可复现、越界会报错** = **通过**（值得搬）；报错/结果离谱 = **不通过**。
- [ ] **3. 和 COROS 官方跑力对拍**：用它 `vdot_calculator` 用你最近一场成绩算 VDOT，与高驰 App 的"跑力/VDOT"比对。成本 ¥0。
  - 判定：两者接近（同档） = **通过**（可放心用）；差很多 = **半通过**（需查口径，别直接上产品）。
- [ ] **4. 看一眼打卡图**：让它生成一张周打卡图，浏览器打开看视觉。成本 ¥0。
  - 判定：**想照着做**（甚至想直接用于自己的看板） = **通过**；觉得平平 = **半通过**。
- [ ] **5. 需求确认（最关键）**：问自己——"我打开这个产品，最想看到的是**数据**，还是**下周该练什么**？"
  - 判定：只想看数据 = **维持看板定位**（做 B/C/E）；想要建议 = **进入教练方向**（先 A 再议 F）。

> **决策规则**：1 + 2 通过 → 借鉴 B/C 有底；4 通过 → 追加 E；5 若"想要建议"占上风 → 才考虑 F。

## 六、隐藏坑（预期落差 / 政策时效 / 平台限制）

1. **形态错位（最大坑）**：它是 **Claude Skill，不是产品**。它**没有硬件门槛之外的网页**，非 Claude/无 MCP 环境体验很差（README 自认 DeepSeek/Kimi 等**不支持 MCP**）。**别指望"克隆下来就有一个像我们这样的产品"。**
2. **课表回写手表做不到（已由它自己证实）**：`ADAPTERS.md` 明写高驰 MCP **全为只读**，`createTrainingPlan / updateTrainingPlan` 等写工具一律返回 `Unknown tool`。所以"排好课表自动推到手表"**目前不可能**——只能出 Markdown 或图。想做"回写"请另寻渠道。
3. **脚本 Python 版本坑（已实测，见附录）**：本机 `python3` = **3.9.6**，而 `readiness_calc.py` / `nutrition_calc.py` 用了 `float | None` 写法（Python **3.10+**）→ **直接报 `TypeError`**。搬进来**必须先改**（换成 `Optional[...]`）。
4. **`parse_fit.py` 要第三方库**：它 `import garmin_fit_sdk` / `fitparse`——**违反我们"零第三方依赖"的项目规则**。若要用它的 FIT 解析，需自行改造。
5. **合规红线**：它的伤病/营养内容属**健康建议**，我们的红线是「**不做医疗诊断、结论标"仅供参考"**」。借鉴内容时必须改写口径，尤其伤病分级那几卡。
6. **时效性**：它自己标注"模型能力档位核对日期 **2026-07**"，会过期；`ADAPTERS.md` 也提示 `querySportRecords` 有 **40–50% 偶发 404**、FIT 直链**每日限 50 个**——这些坑我们若抓数据也会遇到。
7. **同源问题**：既然用**同一套官方 MCP**，它遇到的接口变动、限额，**我们一个都跑不掉**——别把它当"另一套更稳的数据源"。
