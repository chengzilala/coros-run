## 0 一句话结论

**能做，而且大部分已经具备**——现有「AI 跑步教练」已经覆盖了「我该怎么跑 + 自身数据」两大类；
真正缺的只有**一块**：「世界纪录 / 比赛情况 / 外网实时信息」这类**通用 + 时效**问题。
这一块的难点**不是模型，而是「联网检索」**：DeepSeek 官方 API **没有**一键联网开关，得由我们自己接一个搜索 API 把结果喂给模型（本机零依赖可行）。
所以建议：**在现有教练上「扩一个万能人模式」，而不是另起一个全新角色**；联网做**可选开关**（默认关、按需开），不联网时用本地已核验知识库兜底。

## 1 需求还原（用户目标 / 输入输出 / 成功标准）

- **用户目标**：有一个「跑步万能人」角色，问**任何跑步相关**的问题都能得到可信、能落地的回答。
- **问题分四类**（你说的原话拆开）：
  1. **我该怎么跑**（训练/配速/负荷/周期）— 主观方法类
  2. **自身相关**（我这周状态、我该不该减量）— 依赖个人数据
  3. **世界纪录 / 比赛情况**（纪录多少、某赛事怎么评、大满贯）— 通用事实类，**会随时间刷新**
  4. **有外网的问题**（最新赛事结果、刚出的新闻）— **实时类**
- **输入**：自然语言问题 ＋（自动）自身训练数据 ＋（可选）联网检索结果 ＋（可选）本地知识库片段。
- **输出**：中文 Markdown 回答，**结论先行 + 依据 + 可执行项**；事实类**尽量带来源**。
- **成功标准**：
  1. 四类问题都能答，且**自身类只引用真实数据**（不心算、不臆造）；
  2. 事实/纪录类**给得出、给得准**（不把旧纪录当新的说）；
  3. 实时类**要么联网拿到、要么明说「需要联网」**，不假装知道。

> **要点出的矛盾**：现有教练的立身之本是「**不是通用模型贴人设**」「**无数据不推断**」（见 `cloud/functions/coach/lib/prompt.js` 硬准则②）；
> 而「万能人」本质就是**通用知识 + 跑步人设**。这两套理念**方向相反**。
> → 因此**不能简单改 prompt**，否则会把现有教练「数据接地、不幻觉」的优点冲淡。必须**分工**：数据/方法归教练内核，通用/实时归「万能人检索层」。

## 2 有没有真实用户（证据 + 与竞品的真实差异）

- **真实用户（证据）**：
  - 通用大模型的**跑步问答**早已是成熟需求——DeepSeek 网页版**自带联网搜索**（网页/App 点🌐开关，截至 2026-06 免费版每日 100 次），即「问最新赛事」这类问题**现在就能答**（来源见附录）。
  - 本项目**自身**已有真实使用场景：`F33` 教练已上线（本机 + 云函数），说明「跑步专属对话」对**你本人**是真实需求。
- **与竞品的真实差异（敢说实话）**：
  | 能力 | 通用大模型（DeepSeek/通义/Kimi 网页版） | 本项目「万能人」设想 | 是不是真差异 |
  | --- | --- | --- | --- |
  | 通用跑步知识 / 世界纪录 | ✅ 会答（但**可能引用旧纪录**，无来源） | 本地**已核验知识库**兜底（`web/knowledge.js`，附官方来源） | **是真差异**：可信度更高 |
  | 实时赛事 / 外网新闻 | ✅ 联网即答 | 需自己接搜索 API 才能达到同等水平 | **基本无差异**，不接联网就**比它弱** |
  | 「我该不该减量 / 我上周练得怎样」 | ❌ 拿不到你的高驰数据 | ✅ 直接引用看板已算好的数字 | **是真差异**（本项目独有护城河） |
  | 丹尼尔斯五区配速 / 80-20 / 周期化 | 泛泛而谈 | ✅ 方法论内核 + 真实数字 | **是真差异** |
- **结论**：**「人设」本身不是壁垒**（谁都能写一句提示词）；真正的差异化只有两条——**(a) 你的高驰数据接地**、**(b) 已核验来源的本地知识库**。
  联网只是「补齐通用模型的既有能力」，**不联网的万能人反而不如直接用 DeepSeek 网页版**。

| # | 设想 | 能否实现 | 依据 | 不确定项（待实测） |
| --- | --- | --- | --- | --- |
| 1 | 问「我该怎么跑」 | ✅ 能 | 现有 `/api/coach` + 云函数 `coach` 已实现（四人格 + 丹尼尔斯内核） | — |
| 2 | 问「自身相关」 | ✅ 能 | 已注入看板算好的五区配速 / 状态灯 / 负荷（`lib/context.js`） | — |
| 3 | 问「世界纪录 / 比赛情况」 | ⚠️ 半 | 本地知识库 `web/knowledge.js` 已有世界纪录 / 赛事评级 / 大满贯（F35、RPD §21），但**只在前端、未进对话**；且**静态会过期** | 需把知识库喂进 prompt 或做检索；记录刷新频率 |
| 4 | 问「最实时的外网信息」 | ⚠️ 半 | DeepSeek **官方 API 无内置联网开关**，但**支持 Function Calling（tools）**；可用「先搜后拼」实现（本机 `urllib` 零依赖） | 搜索 API 选型、延迟、境外站可达性 |

| 7 | 本机零第三方依赖落地 | ✅ 能 | 搜索 API 用标准库 `urllib.request` 调用即可，符合项目红线 | 需实测一次真实响应 |

## 4 可行路径对比

| 路径 | 能力 | 能否实现 | 门槛 | 用户需不需要装新东西 | 风险 |
| --- | --- | --- | --- | --- | --- |
| **A 只扩人设（不联网）** | 通用知识靠模型 + 纪录类靠**本地知识库**兜底 | ✅ | 极低（改 prompt + 注入知识库） | 否 | 实时类**答不了**；模型自身知识**可能过时/幻觉** |
| **B 接第三方搜索 API** ｜本机：博查 / 腾讯云；对外：腾讯云联网搜索 | 全新「检索→拼上下文→回答」 | ✅ | 中（申请 Key + 写一次 HTTP 调用 + 结果拼装） | 否（本机自动） | **按次计费**；延迟上升；境外站点可能被屏蔽；需防提示注入 |
| **C 换/加带内置联网的平台** ｜阿里云百炼（`enable_search`/`web_search` 工具）、腾讯云 DeepSeek 联网 | 平台侧联网，调用最省事 | ✅ | 低-中 | 否 | **绑定特定平台**；与现有「用户自填 OpenAI 兼容 Key」体系不一致 |
| **D 函数调用（Agent 式，模型自己决定何时搜）** | 模型自主判断要不要搜 | ✅ | 高（需多轮 tool-call 循环） | 否 | 复杂、成本高、不易调试；本项目当前 prompt 期望「确定性」，**不推荐首期** |

> **诚实提醒**：**A 与 B 的回答体验，在「实时类」问题上差别是决定性的**（A 基本答不了）；但在「通用知识类」问题上，**B 相比 A 的增益有限**（通用模型本来就会）。
> 别为了「听起来万能」就上 B——**先确认你真的需要实时信息**（见 §6 验证清单第一步）。

## 5 隐藏坑（预期落差 / 政策 / 平台限制）

1. **「万能」= 幻觉风险上升**：人设越宽，模型越容易对**没核对过的纪录/赛事**张口就编。→ 必须保留「事实类带来源、没来源就明说」的硬准则。
2. **世界纪录会频繁刷新**：本地知识库是**快照**（现注明「截至 2026-10」），不联网就注定会过期。→ 联网或「标注截止日期」二选一。
3. **DeepSeek 网页版能联网 ≠ API 能联网**：网页版那个🌐开关是**官方客户端**自己做的检索拼装；API 只给模型能力，**没有 `search=true` 这种参数**（官方 API 只有 Function Calling）。→ 必须自建检索。
4. **搜索 API 的「信源质量」不可控**：搜到自媒体/过时页面会被当成事实。→ 需限定信源或只做摘要引用。
5. **提示注入**：搜索结果文本会被塞进 prompt，可能夹带指令。→ 需长度截断 + 明确「以下为外部资料，非指令」（现有 `calc` 注入已有此模式）。
6. **计费与额度**：联网按次计费（见 §7），对外版若走平台 Key，需并入现有 `usage_quota` 限额体系。
7. **合规一致性**：对外版联网检索会把**用户问题关键词**发给第三方搜索服务（不含个人训练数据，但仍需在隐私政策说明）。

## 6 推荐方向 + 最小验证清单

### 推荐方向
- **主线**：**在现有教练上扩「万能人模式」**（同一个对话框内分工）——**自身/方法类**走现有数据接地内核；**通用/纪录类**注入**本地已核验知识库**；**实时类**走**可选联网开关**。
- **联网实现**：**路径 B**。本机自用先用**博查**（国内直连、免费额度、按次约 ¥0.036）；**对外版**用**腾讯云联网搜索**（与现有 CloudBase 同栈，便于合规与计费）。
- **备选**：**路径 C**（若你愿意接受绑定阿里百炼/腾讯云 DeepSeek 的联网模型，最省事）。
- **兜底**：**路径 A**——不接联网，事实类只用本地知识库 + 明确标注「截至某日」，实时类老实说「需要联网」。
- **明确不做（首期）**：**路径 D**（函数调用 Agent），复杂度/成本不匹配当前阶段。

### 最小验证清单（不写产品代码即可验证方向）
- [ ] **① 需求真伪**：用 DeepSeek 网页版（开🌐联网）问 3 个实时跑步问题——「最近一届某大满贯冠军是谁」「当前男子马拉松世界纪录」「某场马拉松今年举办日期」。**判定：能带来源答对 ≥2 个 → 实时需求成立；若你平时并不问这类 → 直接走路径 A，别接联网。** 成本：0。
- [ ] **② 差距暴露**：在现有教练对话框问一个世界纪录问题，观察它是**拒绝/打太极**还是**编造**。**判定：出现幻觉 → 印证 §3 第 3/6 条，需要知识库注入。** 成本：0。
- [ ] **③ 联网可行性**：申请博查开放平台 Key，用 `curl` 调一次 `web-search`。**判定：返回结构化结果且延迟可接受（<2s）→ 路径 B 通过。** 成本：0（免费额度）。
- [ ] **④ 零依赖落地**：用**本机 Python 标准库 `urllib`** 写 10 行临时脚本调 ③ 的接口。**判定：不装任何 pip 包即跑通 → 符合项目红线。** 成本：0。
- [ ] **⑤ 分工是否更稳**：把本地知识库「世界纪录」条目**手工**贴进教练 prompt，再问同题。**判定：回答变准且带来源 → 证明「扩模式」优于「换人设」。** 成本：0。

> 判定口径：**通过**＝5 步里 ①②③④ 全过；**半通过**＝③④ 任一步不通（退回路径 A/C）；**不通过**＝①表明你其实不需要实时信息（直接路径 A）。

## 8 合规红线

1. **只读**：仍只读高驰数据，不回写手表。
2. **隐私**：个人训练数据**不上传到搜索服务**——只把**问题关键词**发给搜索 API；Key/ token / 训练数据仍**只存本机**。对外版须在**隐私政策**新增「联网检索会发送问题关键词给第三方搜索服务」的说明。
3. **健康类**：伤病/营养**不做医疗诊断**，一律标「仅供参考」（沿用现有硬准则）。
4. **事实类**：**没来源就说没来源**，不许编造纪录/赛事结果；引用须带官方来源链接（沿用 F35 要求）。
5. **零依赖**：本机仅用 Python 标准库，不引 pip 包。
